# LyricShiori CPU、安全与性能诊断

日期：2026-09-06。源码基线：`3c5cab1`。运行实例：`/Applications/LyricShiori.app`，0.3.0 (18)，PID 64336，macOS 27.0 beta。源码与已安装二进制未做逐字节一致性验证，但采样符号与源码中的热点函数和行号对应。

本次进行运行进程采样、第一方 Swift 代码与构建/发布脚本静态检查、依赖配置检查及现有测试验证。未改动应用代码、设置或安装包，也未向运行实例发送破坏性请求。此报告不等于完整渗透测试或全部第三方依赖的漏洞认证。

## 运行证据

- `ps` 瞬时读数：CPU 189.7%，约占两个逻辑核心。
- 5 秒 `sample`：物理内存 footprint 116.2 MB，峰值 139.3 MB；单次采样不能证明没有内存泄漏。
- 原始证据：[调用栈采样](2026-09-06-cpu-sample.txt)。其中多个网络连接队列反复执行 `nw_connection_add_read_request_on_queue → nw_read_request_fail`；业务回调又进入 `SharedLyricsCacheServer.receive`。
- 主线程存在 `WordVerticalLyricTextView.draw → layoutUnits`、Core Text 排版和字形阴影卷积；后台还存在 `encodedLocalEntry → LocalLyricsStorage.loadLyrics`。
- 这些是采样中真实出现的热点；未执行修复前后 A/B 测量，因此不宣称各项的精确 CPU 占比或预期降幅。

## 需要优先修复

### 1. P1：桥接连接失败后仍继续读取，形成忙循环（运行证据支持）

位置：`Sources/LyricShiori/Services/SharedLyricsCache.swift:875,882,898`。

`receive` 回调将第四个参数 `NWError?` 丢弃；只要请求不完整且 `isComplete == false`，就继续提交读取。连接失败或五秒超时取消后，读取可能立即回报错误，代码又重新读取。同一失效连接上的反复失败在本次采样中可见。这是当前持续高 CPU 的首要修复项；接收发生在 HTTP 身份校验之前，也有本机拒绝服务风险。

建议：错误必须终止接收并取消连接；EOF 不完整请求直接结束；连接跟踪应保证取消后不会再次调度，并在 server.stop 时清理所有已接受连接。增加半截请求后断开、RST、超时、停止服务的测试，检查回调不再增长，不能只测试完整 HTTP 请求。

### 2. P1：缓存时间戳校验可整数溢出（静态确认）

位置：`Sources/LyricShiori/Services/SharedLyricsCache.swift:732`。

`expiresAt > cachedAt` 不能保证 `expiresAt - cachedAt` 可表示。例如 `cachedAt = Int64.min`、`expiresAt = Int64.max` 都是合法 JSON 整数，前一条件为真，减法却溢出，Swift 触发 trap 而非抛出可捕获错误。`saveEncodedEntry → save → isValid` 可到达该路径。另见 `compareLocalPersistencePriority` 的 `cachedAt` 相减。

建议：使用 `subtractingReportingOverflow` 或安全边界比较；时间戳限定合理范围，排序用大小比较替代减法。补充 Int64 极值及超大有限浮点时间值的测试。未向用户正在运行的服务发送此输入。

暴露范围：服务绑定 127.0.0.1，并有 Origin 白名单；但无 Origin 的本机客户端可以从 `/bridge-session` 获取 token，因此 token 不能认证“可信本机插件”。不能将此问题表述为已证实的互联网远程执行漏洞。

### 3. P1：更新安装缺少发布者身份校验（静态及签名检查确认）

位置：`Sources/LyricShiori/Services/GitHubUpdateService.swift:192`；`Scripts/build-app.sh`。

安装器只检查 Bundle ID 和 `codesign --verify --deep --strict`。构建脚本使用 `--sign -`；当前安装实例也显示 `Signature=adhoc`、无 TeamIdentifier。这能检查包的签名结构与完整性，不能证明来自指定发布者。若 Release 资产被替换为另一个同 Bundle ID、自行签名的包，此检查不提供独立的发布者防线；安装器还可能请求管理员权限。

建议：固定 Developer ID/Team ID 的可信 requirement，或使用内置公钥验证独立的更新签名。单独从同一受损发布渠道获取 SHA256 不等价于发布者认证。HTTPS 和 GitHub 域名约束已有价值，问题不意味着普通网络旁路即可替换包。

依据：[Apple TN3127，代码签名 requirement](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)。

## 其他性能与可靠性问题

### 4. P2：竖排歌词每帧重新排版与阴影绘制（运行证据支持）

位置：`UI/DesktopLyricsView.swift:126`；`UI/WordVerticalTextRenderer.swift:58,80,175`。

播放时每列都使用 60 Hz TimelineView，仅根据 `line.isPlaying` 暂停；非当前歌词列也收到 true。每次 configure 无条件 `needsDisplay = true`，draw 重建 layoutUnits，再对每个字/词创建 framesetter/frame，并绘制阴影。当前词甚至对进度为 0 的透明叠层仍构造排版并绘制。采样显示字形阴影进入 vImage 卷积，伴随额外工作线程。

建议：按文本、字体、timing 缓存排版和可复用绘制资源；非当前列保持静态，仅在内容/样式变化时刷新；进度为 0/1 时跳过无效绘制；考虑使用缓存字形图层进行动画。先保持视觉效果，再做同曲目、同字号、同行数的 A/B 测量。

### 5. P2：桥接 GET 每次扫描目录并重新解析本地歌词（运行证据支持）

位置：`Services/SharedLyricsCache.swift:1034,1068`；`Services/LocalLyricsStorage.swift:144,163,177`。

每次请求优先调用 localStorage.loadLyrics。candidateURLs 在读取标准路径之前就枚举整个目录；随后完整读文件、解码 JSON、识别语言和归一化，再编码返回。桥接重复查询时放大 I/O 和 CPU。本次两个后台线程栈均可见这条路径。

建议：先读标准路径，必要时才枚举；按路径和修改时间缓存文档及响应，写入后失效，外部修改也需检测；可合并同一歌曲的并发请求。SharedLyricsCache 的内存缓存无法消除这条独立的本地存储路径。

### 6. P2：更新先删旧应用再复制，失败无法回滚

位置：`Services/GitHubUpdateService.swift:201`。

磁盘满、权限错误或复制失败时，旧应用已被 rm 删除，可能只剩缺失或不完整的新应用。安装前应完成验证及暂存，再进行替换并保留回滚副本，覆盖管理员安装分支。

### 7. P2：导入、解析及部分图像处理在主线程且缺少资源上限

位置：`App/LyricShioriStore.swift:567,910,929`；`Services/LocalLyricsStorage.swift:214`。

同步 importLyrics 完整读取文件并解析，未限制文件大小、行数、每行字符数及词时间数量。本地 LRCS 解码不经过桥接 isValid，巨型导入可以造成主线程卡顿和内存压力。自动配色的下载后解码也在 MainActor 上，并使用原图解码；artworkPresetCache 无容量上限。

建议：读取前限制大小，解析后限制结构；在后台执行纯解析/图像解码；缩略图下采样后再取色；图片缓存设上限。对所有将 Double 转成 Int 的持久化/显示路径验证有限性和可表示范围。

### 8. P2：不需要滚动时仍有常驻刷新

位置：`Infrastructure/MenuBarController.swift:351`；`UI/DesktopLyricsWindowController.swift:140`。

菜单栏仅凭“正在播放”启动 60 Hz Timer，歌词完全能放下时也重绘、测量文本；鼠标经过隐藏功能启用后每 16 ms 查询指针位置。建议菜单栏仅溢出且处于滚动阶段时刷新；指针检测可用事件驱动或降低轮询频率。这些属于附加开销，不能单独解释本次 190% CPU。

## 其他检查与边界

- 网络已有 HTTPS、超时、回环绑定、Origin 白名单、单请求大小限制；文件名有目录分隔符处理；缓存写入为 atomic，条目数量限制 80，手动重置记录限制 200。这些不应误报为完全没有保护。
- 桥接未限制并发连接/请求速率；资源上限应按服务总体预算设置，而非只限制单请求。
- SkyLight 私有 API 通过 dlsym/unsafeBitCast 调用，存在系统升级兼容风险；本次没有发现其为 CPU 主热点的证据。
- 检查了 Package.resolved 与直接相关 LyricsKit 网络路径，未进行完整依赖 CVE 数据库比对或全部传递依赖源码审计，不能宣称“依赖无漏洞”。
- 建议执行顺序：连接错误终止 → 时间戳/数值边界 → 竖排缓存与桥接读缓存 → 更新身份校验和事务替换 → 其余资源限制与刷新优化。
